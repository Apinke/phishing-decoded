CH.01 — ANATOMY OF A PHISHING ATTACK
// The attack lifecycle — from target selection to credential harvest
// Phase 1: Reconnaissance
attacker.scrape(["LinkedIn","Facebook","company_website"])
target = { name: "Kemi", email: "kemi@techcorp.ng", role: "Finance" }

// Phase 2: Infrastructure
domain = register("techcorp-finance-portal.com") // typosquat
cert = getLetsEncrypt(domain) // free TLS cert

😈
Phase 3: Delivery. Personalised spear-phish sent to kemi@techcorp.ng referencing her real projects from LinkedIn.
// Spear phishing uses OSINT to craft targeted, convincing messages
😰
The email references my actual project name and my manager's name... This must be legit!
// Social engineering exploits trust and context to override critical thinking
CH.01
Attack Lifecycle
Reconnaissance: Attackers harvest OSINT (Open Source Intelligence) — LinkedIn, company websites, social media — to personalise attacks.
Infrastructure: Lookalike domains + free TLS certificates create sites that appear legitimate. The padlock no longer means safety.
Spear Phishing: Unlike mass phishing, spear phishing is targeted. It references real names, projects, and contexts to defeat scepticism.
Defence: Train users to verify the URL independently of email content. Context-aware messages are not proof of legitimacy.

// How to dissect a suspicious URL

// Breaking it down:

subdomain: techcorp-ng-secure-login // NOT the domain — it's a trick
real domain: verification.ru // ← THIS is who owns this URL
path: /auth // credential harvesting endpoint
// LEGITIMATE vs FAKE — spot the pattern:
INDICATORLEGITIMATEPHISHING

AgeYears oldRegistered today
💡
Rule: Read the URL right-to-left from the first single slash. The domain immediately to the left of the first / is the REAL owner.
CH.02
URL Analysis
Domain vs Subdomain: In "bank.phishing.com", the domain is phishing.com — not bank. The leftmost part of a URL is the least significant.
HTTPS is not safety: TLS certificates are free and automated. Any phishing site can have a padlock. It means encryption, not legitimacy.
Domain age matters: Check WHOIS — legitimate brands have domains registered years ago. Phishing domains are often hours or days old.
Practical check: Hover over links before clicking. On mobile, press-and-hold to preview the URL before tapping.

CH.03 — EMAIL HEADER ANALYSIS
// Analysing what the email client hides from you
From: "GTBank Security" <security@gtbank.com> ← display name spoofed
Reply-To: harvester@phish-collector.xyz ← replies go HERE
Return-Path: bounce@smtp-farm-23.ru ← reveals real sender
X-Originating-IP: 185.220.101.47 ← Russian datacenter IP
Received: from smtp-farm-23.ru ← actual sending server
// The "From" display name can be anything — check Return-Path and Received headers
// Email Authentication: SPF, DKIM, DMARC
Authentication-Results: mx.google.com;
  spf=fail (domain of gtbank.com does not designate sender)
  dkim=fail (signature verification failed)
  dmarc=fail p=reject
// A DMARC fail on a bank email = immediate red flag. Real bank = SPF/DKIM/DMARC pass.
CH.03
Email Authentication
SPF (Sender Policy Framework): A DNS record specifying which servers can send email for a domain. SPF fail = sender not authorised.
DKIM (DomainKeys Identified Mail): Cryptographically signs email content. DKIM fail = email was modified in transit or forged.
DMARC: Tells receiving servers what to do with SPF/DKIM failures — none, quarantine, or reject. Check header "Authentication-Results".
How to check: In Gmail, click the three dots → "Show original" to see full headers. Look for Authentication-Results.

CH.04 — DGA AND AI-GENERATED DOMAINS
// Domain Generation Algorithms — how malware finds its C2 servers
// Simple DGA — date-seeded random domains
seed = date(2026,05,26) // today's date
domains = generate(seed, count=500)
// Result: xkqpvzlb.com, e3raciomg.net, a1b8ccmd.org

// AI-enhanced DGA — trained on real domains
model = LSTM(trained_on=10M_real_domains)
domains = model.generate(seed, count=500)
// Result: cloudsync-update.net, securelogin-portal.com
// ↑ Low entropy — defeats signature-based detection!
🤖
Old DGA: entropy 4.2 bits/char → DETECTED. AI-DGA: entropy 3.1 bits/char → mimics real domains → evades detection.
// Detection signals for AI-DGA phishing domains:
domain age < 24h no historical traffic bulk registration pattern no MX records shared hosting IP cert issued today
CH.04
AI-Powered Phishing Domains
DGA Basics: Malware uses algorithms seeded with the date to generate hundreds of domains daily. Only attackers know which ones are active.
AI-DGA: Neural networks trained on legitimate domain corpora generate domains with natural linguistic properties — defeating entropy analysis.
Detection signals: Domain age (WHOIS), certificate transparency logs (crt.sh), IP reputation, absence of historical DNS queries.
Tool: Check crt.sh for a domain's certificate history. A cert issued seconds before a suspicious email is a strong indicator of a phishing campaign.

BEC (Business Email Compromise): attacker impersonates CEO and asks finance team to wire funds urgently. $2.7B lost globally per year.
// BEC exploits authority + urgency + trust — highest-value phishing variant
CH.05
Social Engineering
Cialdini's principles: Phishing systematically exploits authority, urgency, scarcity, social proof, fear, and reciprocity to bypass rational thinking.
BEC (Business Email Compromise): The most damaging phishing variant. Attackers impersonate executives to authorise fraudulent wire transfers.
Out-of-band verification: Any unexpected financial request, regardless of apparent sender, must be verified through a separate, established communication channel.
Security culture: Employees must feel safe saying "I need to verify this" without fear of seeming difficult. A verification culture is your strongest BEC defence.

CH.06 — MFA AND ITS LIMITS
// Multi-Factor Authentication — what it stops and what it doesn't
// MFA factors:
factor1 = "something you KNOW" // password
factor2 = "something you HAVE" // phone/token
factor3 = "something you ARE" // biometric

// MFA STOPS: password-only attacks, credential stuffing
// MFA BYPASSED BY: real-time phishing proxy (AiTM)
// AiTM (Adversary-in-the-Middle) phishing bypasses SMS/TOTP MFA:
victim → phishing_proxy → real_site
victim enters: password + OTP code
proxy forwards credentials in real-time
proxy receives: session_cookie
// Attacker now has authenticated session — OTP useless!
🛡️
FIDO2/Passkeys are phishing-resistant — the credential is bound to the origin domain. A phishing proxy cannot forward it to the real site!
// FIDO2 hardware keys and passkeys are the gold standard against AiTM attacks
CH.06
MFA & Phishing Resistance
MFA is essential but SMS and TOTP (time-based one-time password) codes can be intercepted by real-time phishing proxies (AiTM attacks).
AiTM attacks use reverse proxies (Evilginx2, Modlishka) to relay credentials and session tokens in real time, defeating OTP-based MFA.
Phishing-resistant MFA: FIDO2 hardware keys (YubiKey) and passkeys bind authentication to the origin domain. A phishing domain gets nothing.
Recommendation: Use FIDO2/passkeys for privileged accounts. SMS MFA is better than nothing but should be upgraded where possible.

CH.07
Threat Intelligence
IOCs (Indicators of Compromise) are evidence of an attack — domain names, IPs, URLs, email addresses, file hashes. Share them to protect others.
MISP and OpenCTI are open-source threat intelligence platforms for sharing and correlating IOCs across organisations and sectors.
Certificate Transparency: All TLS certificates are logged publicly. Searching crt.sh for your brand name reveals lookalike domains as they are created.
Proactive monitoring: Set up alerts on crt.sh and domain registration feeds for your brand name to catch phishing infrastructure before it's used.

CH.08
ML-Based Detection
Feature engineering: Effective ML phishing classifiers combine lexical (domain structure), temporal (age), infrastructure (IP/ASN), and certificate features.
DNS-layer blocking: AI at the DNS resolver level (Cloudflare, Cisco Umbrella, Quad9) blocks malicious domains before any TCP connection is established.
Zero-hour detection: Models trained on domain registration metadata can classify never-before-seen phishing domains at first query with >95% accuracy.
Adversarial robustness: Ensemble models combining lexical, graph, and behavioural features are harder to evade than single-feature classifiers.

No single layer is sufficient. A phishing email that bypasses the gateway, passes DNS filtering, and reaches a user with weak MFA can still succeed.
// Layered defence assumes each control will sometimes fail — depth provides resilience
CH.09
Defence in Depth
DMARC at enforcement (p=reject): Prevents your domain from being spoofed in phishing campaigns. Check your domain's DMARC record — many organisations don't have it.
DNS-layer protection: Deploy AI-powered DNS filtering (Cloudflare Gateway, Quad9) to block phishing domains before users can navigate to them.
SOAR integration: Automated playbooks triggered by phishing detections can quarantine emails, block domains, isolate endpoints, and notify users within seconds.
Metrics that matter: Track phishing simulation click rates by department, time-to-report, and credential submission rate — these reveal training effectiveness.

CH.10
IR Playbook
Immediate containment: Isolate the endpoint and revoke active sessions before the attacker can pivot to other systems.
Credential reset: Assume all credentials entered on the phishing site are compromised. Reset all passwords and enforce MFA upgrade.
Lateral movement prevention: Check for any unusual authentication events in the 24 hours following the click — attackers often move quickly.
IOC sharing: Share phishing domain, IP, and email sender details with your sector ISAC, AfricaCERT, and the impersonated organisation's abuse team.
